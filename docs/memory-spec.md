# Embarsy Memory — спецификация

Статус: черновик v0.1 для обсуждения · 2026-10-11

Раздел **Memory** в Embarsy даёт агентам (Claude Code, Codex, Zoo / Roo Code) одну общую память — ядро инструкций, скиллы, знания, опыт — и даёт человеку экран, где эту память видно, можно разобрать и привести в порядок. Документ фиксирует формат базы, правила публикации агентам, интерфейс, онбординг и порядок работ.

---

## 1. Проблема

Разобрано на реальной системе (`~/.agents/skills` + личная папка скиллов `~/notes/.agents/skills`, октябрь 2026):

- **Нет источника истины.** Три копии скиллов (личная папка, `~/.agents/skills`, globalStorage Zoo) разошлись в 37 местах; правило безопасности, добавленное в одну копию, не дошло до агента, читающего другую. Истории изменений нет.
- **У каждого агента своя память.** Claude Code не видит общих скиллов вообще и ведёт отдельную auto-memory; факты дублируются и противоречат друг другу.
- **Скиллы используются как база данных.** Знания, журнал опыта и профили людей упакованы в `SKILL.md` + `references/`; каждую запись регистрируют руками в трёх индексах — расхождение гарантировано.
- **Способности спрятаны** в `references/` и не участвуют в штатном обнаружении скиллов агентом.
- **Постоянный налог на контекст** ~38 КБ (~10k токенов) на каждую задачу, при этом «ALWAYS use first» в description не гарантирует загрузку.
- **Скиллы молча отбрасываются**: Zoo игнорирует скилл, если `name` ≠ имя папки (5 скиллов), Claude и Zoo не видят вложенных папок.
- **Хрупкие ссылки** с номерами строк (`SKILL.md:36`) — 256 штук.

## 2. Цели и не-цели

**Цели**

1. Одна база на диске — единственный источник истины для всех агентов.
2. Каждый поддерживаемый агент получает ядро, скиллы, чтение знаний и путь записи — штатными для него механизмами.
3. Человек видит, что каждому агенту видно и почему нет, и разбирает то, что агенты предлагают запомнить.
4. Онбординг для любого пользователя: с нуля или миграция из существующих папок.
5. Здоровье базы проверяется автоматически: расхождения, дубли, битые ссылки, устаревание.

**Не-цели (v1)**

- Свой markdown-редактор и граф. Редактирование — кнопкой «Open in editor».
- Синхронизация между машинами и командная память. База — папка; git — по желанию пользователя.
- Дообучение моделей (см. §10).
- Obsidian как зависимость. Формат совместим с Obsidian, но не требует его.

## 3. Принципы

1. **Файлы — истина, Embarsy — ускоритель.** База — обычный markdown в обычной папке и работает, даже если Embarsy выключен или удалён.
2. **Агентам — плоско, человеку — как удобно.** Внутри базы любая структура; агентам публикуется плоская витрина симлинков по общему минимуму требований (§4).
3. **Ссылки — для агентов.** Обычные относительные markdown-ссылки без номеров строк: агент открывает их без поиска; GitHub, VS Code и Obsidian их понимают.
4. **Ничего не удаляется молча.** Перед записью — предпросмотр, перед изменением чужих мест — бэкап, у каждой операции — Undo. Удаление старых мест — отдельный шаг с подтверждением.
5. **Embarsy трогает только своё.** Он владеет только ссылками и файлами, которые сам создал (журнал в `.embarsy/exposure.json`); чужие настоящие папки не перезаписывает, а предлагает «забрать».
6. **Применение — только человеком.** MCP-инструменты агентов могут предлагать (inbox, план миграции), но применить план к файловой системе можно только кнопкой в UI.
7. **Локально по умолчанию.** Сам Embarsy ничего не отправляет в сеть (обещание README «Nothing ever leaves your Mac»). Шаги, которые выполняет облачный агент пользователя, явно помечены (§10).

## 4. Как агенты находят скиллы и инструкции

Проверено по коду и документации; версии: Claude Code — docs code.claude.com (октябрь 2026), Codex 0.142.5 (исходники `rust-v0.142.5`), Zoo Code 3.86.0 (`dist/extension.js`).

| | Claude Code | Codex | Zoo / Roo Code |
|---|---|---|---|
| Глобальные скиллы | `~/.claude/skills` | `~/.agents/skills`; устаревшая `~/.codex/skills` | `~/.agents/skills`, `~/.roo/skills` (+ `skills-<mode>`) |
| Проектные скиллы | `.claude/skills` вверх до корня репо | `.agents/skills` от корня репо до cwd | `.agents/skills`, `.roo/skills` в cwd |
| Глубина | 1 уровень | до 6 уровней | 1 уровень |
| `name` = имя папки | по факту да (имя папки = имя вызова) | не проверяется | **обязательно, иначе скилл отброшен** |
| Формат `name` | — | ≤ 64 символа | `^[a-z0-9]+(-[a-z0-9]+)*$`, ≤ 64 |
| `description` | ≤ 1536 в листинге | обрезается до 1024 | 1–1024, иначе отброшен |
| Симлинк на папку скилла | да (документировано) | да (Repo/User/Admin) | да (`stat` следует ссылке) |
| Коллизия имён | — | показываются оба | `~/.roo` перекрывает `~/.agents`; проект перекрывает глобальное |
| Бюджет листинга | 1% окна; описания режутся с наименее используемых | 2% окна; режутся User-скиллы первыми | не выяснено |
| Глобальные инструкции | `~/.claude/CLAUDE.md`, `@импорты` до 4 уровней | `~/.codex/AGENTS.md` (или `AGENTS.override.md`), ≤ 32 КиБ | `~/.roo/rules/` (рекурсивно, симлинки), глобального AGENTS.md нет |
| Собственная память | auto-memory, переносится `autoMemoryDirectory` | нет | нет |
| Где создаёт скиллы его UI | `~/.claude/skills` | `~/.codex/skills` / `~/.agents/skills` | `~/.roo/skills` (настоящие папки) |

**Общий минимум для витрины:** плоско, один уровень; `name` = имя папки; `^[a-z0-9]+(-[a-z0-9]+)*$`, ≤ 64; description 1–1024 символа; имена уникальны во всей витрине.

**Проверено запуском (2026-10-11, Codex 0.142.5, `codex debug prompt-input` с изолированными `HOME` / `CODEX_HOME`):**

- Codex загружает `~/.codex/AGENTS.md`, когда это симлинк на файл вне `~/.codex`.
- Codex находит скилл, когда `~/.agents/skills/<name>` — симлинк на папку вне `~/.agents`.

**Ещё требует проверки** (по коду и документации вероятно, запуском не подтверждено):

- Watcher Zoo реагирует на изменения за симлинком (нужен ручной тест в VS Code).
- Claude Code разворачивает `@`-импорт из `~/.claude/CLAUDE.md` на путь вне `~/.claude` (документировано; тест требует авторизованного `claude`).

## 5. Формат базы

### 5.1 Дерево

```
~/EmbarsyMemory/                    ← путь по умолчанию; без пробелов (ломает @-импорты и shell)
  memory.yaml                       ← манифест: версия формата, владелец, агенты, движок
  AGENTS.md                         ← СГЕНЕРИРОВАН из core/; руками не править
  core/
    me.md                           ← «Кто я»
    agent.md                        ← «Кто ты»: имя, характер, тон
    rules.md                        ← жёсткие правила и границы
  skills/
    own/<name>/SKILL.md             ← свои
    adopted/<name>/SKILL.md         ← происхождение неизвестно, правятся как свои
    vendor/<source>/<name>/         ← чужие, только чтение
    vendor.lock.yaml
  knowledge/<domain>/<topic>.md
  experience/<YYYY>/<YYYY-MM-DD>-<slug>.md
  people/<Имя>.md
  inbox/
    claude/                         ← = autoMemoryDirectory Claude Code (его формат)
    codex/ · roo/ · manual/
  archive/                          ← заменённое и отклонённое, не публикуется
  .embarsy/                         ← служебное: exposure.json, decisions.jsonl, migration/
  .gitignore                        ← исключает .embarsy/ кроме конфигов
```

### 5.2 Общий frontmatter заметок

```yaml
---
type: knowledge          # knowledge | experience | person | core | inbox
title: Импорт-экспорт в Автохабе
created: 2026-08-14
updated: 2026-10-11
verified_at: 2026-10-11  # когда сверено с источником; основа проверки устаревания
source:                  # откуда факт
  kind: file             # user | agent | file | url | session
  ref: acme-billing-api/docs/...
confidence: observed     # stated (сказал пользователь) | observed (проверено) | inferred (вывод)
status: active           # active | superseded | archived
supersedes: []           # пути заменённых заметок — история не стирается
tags: [billing, payments]
---
```

Обязательны `type`, `title`, `created`. Для `experience` добавляются `project`, `outcome`, `validated_by` (какие проверки прошли). Для `person` имя файла = имя человека.

### 5.3 Ссылки

- Только относительные markdown-ссылки: `[жизненный цикл счёта](../knowledge/billing/invoice-lifecycle.md)`.
- Без номеров строк. Нужен раздел — ссылка на заголовок: `file.md#раздел`.
- Обратные ссылки не хранятся в файлах — Embarsy вычисляет их при индексации.
- Переименование и перемещение — через Embarsy, который переписывает входящие ссылки (H04 ловит пропущенное).

### 5.4 Ядро и `AGENTS.md`

`AGENTS.md` собирается из `core/me.md`, `core/agent.md`, `core/rules.md` и служебного блока «Как пользоваться памятью». Шапка файла: `<!-- generated by Embarsy from core/ — edit core/*.md -->`. Ручная правка ловится проверкой H02.

Бюджет — **≤ 4 КБ** (H06): в ядре только то, что должно действовать всегда. Служебный блок содержит:

- путь к базе;
- «знания ищи через `recall`, при недоступности — grep по папке»;
- «предложить запомнить — через `remember`, только с согласия пользователя»;
- «скиллы — штатно, по описанию».

### 5.5 Скиллы

| Происхождение | Где | Правка | Валидация |
|---|---|---|---|
| `own` | `skills/own/<name>/` | свободно | стиль пользователя (настраиваемый линтер) + минимум §4 |
| `adopted` | `skills/adopted/<name>/` | свободно | только минимум §4 |
| `vendor` | `skills/vendor/<source>/<name>/` | запрещена (H07) | только минимум §4 |

Видимость для агентов задаётся в `metadata` (поле допускается спецификацией Agent Skills):

```yaml
metadata:
  embarsy-agents: "claude,codex,roo"   # по умолчанию — все подключённые
  embarsy-origin: adopted              # для own можно не указывать
  embarsy-adopted-at: "2026-10-11"
```

Для vendor-скиллов видимость и имя в витрине задаются в `vendor.lock.yaml`, потому что их `SKILL.md` не правится.

Доработки чужого скилла делаются отдельным своим скиллом-надстройкой, который ссылается на чужой по имени (пример: `codestyle-e2e-tests` поверх `e2e-tests`).

### 5.6 `vendor.lock.yaml`

```yaml
version: 1
skills:
  e2e-tests:
    path: vendor/acme-qa/e2e-tests
    source:
      kind: git              # git | path | unknown
      url: ssh://...         # для git
      ref: 3f2c1a9           # коммит или тег
      subdir: skills/e2e-tests
    author: sam-rivera
    version: draft           # из metadata скилла, если есть
    tree_sha256: 9b1e…       # хеш файлов при установке → H07
    installed_at: 2026-10-11
    exposed_as: e2e-tests   # другое имя, если исходное нарушает минимум §4
    agents: [claude, codex, roo]
```

Обновление: Embarsy скачивает новую версию, показывает diff и применяет только после подтверждения; `ref`, `tree_sha256` и `installed_at` обновляются.

### 5.7 Каталог скиллов в знаниях

Скилл — полноценный узел каталога без генерации файлов-карточек:

- в заметках на скилл ссылаются по пути к его `SKILL.md`;
- экран Skills и поиск `recall` показывают для каждого скилла происхождение, версию, видимость и обратные ссылки из знаний;
- `recall` индексирует `SKILL.md` всех происхождений (включая vendor), так что агент находит и знание, и скилл, который его обслуживает.

### 5.8 Inbox

Одна заметка = один предлагаемый факт.

```yaml
---
type: inbox
created: 2026-10-11T14:02
agent: codex
proposed_type: experience
proposed_path: experience/2026/2026-10-11-release-acceptance.md
merge_with: []             # пути, с которыми агент предлагает слить
reason: "проверено в сессии: ..."
confidence: observed
---
Текст факта.
```

`inbox/claude/` — это `autoMemoryDirectory` Claude Code в его собственном формате (`MEMORY.md` + файлы с `name/description/type`). Embarsy читает этот формат как inbox. При принятии факта из `inbox/claude/` Embarsy удаляет его строку и из `MEMORY.md`.

Решения по inbox пишутся в `.embarsy/decisions.jsonl` (`inbox-текст → куда / слито с / отклонено`) и используются для подсказок (§10). Этот файл не публикуется и не покидает машину.

## 6. Публикация агентам

### 6.1 Витрина скиллов

| Агент | Куда | Как |
|---|---|---|
| Codex, Zoo / Roo | `~/.agents/skills/<name>` | симлинк на папку в базе |
| Claude Code | `~/.claude/skills/<name>` | симлинк на папку в базе |
| Zoo / Roo | `~/.roo/skills/` | не используется: двойная регистрация даёт дубли, а `~/.roo` перекрывает `~/.agents` |

Правила:

1. Ссылка создаётся, только если имени нет. Если там настоящая папка — это чужое: в Health появляется «забрать в базу?» (H14). После согласия папка переносится в `adopted/`, а на её месте появляется ссылка.
2. Все созданные ссылки записываются в `.embarsy/exposure.json`. Удаляются и меняются только они.
3. Скилл, нарушающий минимум §4, в витрину не попадает, а экран Skills объясняет, какому агенту и почему он не виден (H01).
4. Зарезервированные и системные имена (`skill-creator` у Codex и Anthropic, `synced` у Claude) проверяются на коллизию (H03).
5. Новые скиллы, созданные UI агентов (Zoo → `~/.roo/skills`, Claude → `~/.claude/skills`, Codex → `~/.codex/skills`), обнаруживаются как H14.

### 6.2 Ядро

| Агент | Механизм |
|---|---|
| Codex | `~/.codex/AGENTS.md` → симлинк на `AGENTS.md`. Если в фазе 1 выяснится, что симлинк не читается, — сгенерированная копия + H02 на расхождение |
| Claude Code | строка `@~/EmbarsyMemory/AGENTS.md` в `~/.claude/CLAUDE.md` внутри блока-маркера `<!-- embarsy:memory -->`; остальное содержимое файла не трогается |
| Zoo / Roo | `~/.roo/rules/00-embarsy-memory.md` → симлинк на `AGENTS.md` |

Если исходный файл не пустой, его содержимое уходит в миграцию как кандидат в ядро. Файл заменяется только после подтверждения.

### 6.3 Чтение знаний

- **Основной путь — MCP `recall`** (§7). Мост уже встроен в приложение, конфиги Claude и Codex пишет Connections. Для Zoo / Roo нужно добавить запись MCP в его `mcp_settings.json` (новое в Connections).
- **Запасной путь — grep по базе.** Для него агенту нужно разрешение читать вне рабочей папки: Claude — `permissions.additionalDirectories`; Zoo — авто-одобрение чтения вне workspace; Codex читает и так.

### 6.4 Запись

| Агент | Механизм |
|---|---|
| Claude Code | `autoMemoryDirectory` → `~/EmbarsyMemory/inbox/claude` (user settings) |
| Codex | MCP `remember` (обходит песочницу без расширения прав); запасной путь — `sandbox_workspace_write.writable_roots` |
| Zoo / Roo | MCP `remember` |

### 6.5 Скиллы проектов

Остаются в репозиториях. Claude читает только `.claude/skills`, поэтому для репозитория с `.agents/skills` Embarsy по кнопке на экране Skills создаёт в нём ссылки `.claude/skills/<name>` → `../../.agents/skills/<name>`. Агрегирующий скрипт с копированием и префиксами (`sync-zoo-skills.py`) больше не нужен.

## 7. MCP-инструменты

Добавляются в существующий мост (`tools/embarsy-qdrant-mcp`, бандл в приложении) рядом с `search_code`.

| Инструмент | Что делает | Пишет на диск |
|---|---|---|
| `recall(query, types?, limit=5)` | семантический поиск по базе; ответ — сниппеты с путём, типом, `verified_at` | нет |
| `remember(text, proposed_type?, proposed_path?, merge_with?, reason)` | создаёт заметку в `inbox/<agent>/` | только inbox |
| `memory_status()` | путь к базе, подключённые агенты, число записей в inbox, проблемы Health | нет |
| `memory_scan(sources[])` | инвентаризация источников для миграции (§9.2) | нет |
| `memory_propose(plan)` | сохраняет план миграции в `.embarsy/migration/` для ревью в UI | только `.embarsy/` |
| `memory_history(path, limit=20)` | история файла и построчное авторство из git (§14): дата, агент, источник, кто подтвердил | нет |

Применения через MCP нет — только кнопкой в UI (принцип 6).

В описании `remember` прямо сказано: вызывать, только когда пользователь попросил запомнить или согласился. Это переносит правило согласования в сам инструмент.

Индексация: база индексируется в коллекцию `embarsy-memory` тем же индексатором с чанкингом по заголовкам markdown; watcher переиндексирует изменённые файлы; `archive/` и `.embarsy/` исключены.

## 8. Интерфейс

Новый пункт главной навигации **Memory** между Connections и Monitoring. Внутри — табы в стиле Connections (`tabbedPanel`: выбранный таб открывается в панель).

| Таб | Содержимое | Значок на табе |
|---|---|---|
| **Core** | Формы «Кто я», «Кто ты», «Правила»; предпросмотр собранного `AGENTS.md` и его размер относительно бюджета | — |
| **Skills** | Таблица «скилл × Claude / Codex / Roo»: виден / не виден + причина; происхождение; версия; обновления vendor; оценка бюджета листинга для каждого агента | число невидимых скиллов |
| **Knowledge** | Дерево базы, поиск `recall`, просмотр заметки (WKWebView), обратные ссылки, «Open in editor» | — |
| **Inbox** | Карточки фактов: diff с похожими заметками; «Принять → куда», «Слить с…», «Отклонить» | число записей |
| **Health** | Список проблем (§11) с объяснением и, где возможно, кнопкой исправления | число ошибок |
| **Assistant** | Что локальная модель делает для памяти (миграция, расходящиеся заметки, черновики исправлений) и сама модель: выбор, скачивание, состояние, время простоя | — |

Правила UI проекта:

- у каждого значка состояния (точка, иконка, цвет) есть подсказка при наведении на сам значок;
- оранжевый — только для сбоев, пояснения серые;
- раскрывающиеся блоки открываются кликом по всему заголовку.

Пока базы нет, над табами Skills и Health показывается карточка онбординга (§9), а таба Core нет. Табы Skills и Health работают и без базы — они полезны сразу, поэтому онбординг их не заменяет (изменено при реализации фазы 2).

## 9. Онбординг

Две карточки: **Start fresh** и **Bring existing memory**.

### 9.1 С нуля

1. **Где хранить.** Папка (по умолчанию `~/EmbarsyMemory`); опция «инициализировать git».
2. **Кто я.** Имя; роль; языки общения; как обращаться; стиль ответов; свободный текст.
3. **Кто ты.** Имя агента; характер и тон (пресеты + текст). Границы — переключатели:
   - спрашивать перед любым изменением, кроме чтения;
   - браузер и GUI только по явной просьбе в текущей задаче;
   - не сохранять секреты;
   - отделять факты от выводов.
4. **Агенты.** Найденные Claude / Codex / Zoo с состоянием. Предпросмотр всех изменений: файлы, симлинки, настройки, diff существующих файлов. **Применить** / **Отмена**.

Модель не нужна: ядро собирается шаблоном из полей формы.

### 9.2 Миграция

1. **Источники.** Автоматически найденные места с числом файлов и галочками:
   - `~/.agents/skills`;
   - `~/.claude/skills`, `~/.claude/CLAUDE.md`, `~/.claude/projects/*/memory`;
   - `~/.codex/AGENTS.md`, `~/.codex/skills`;
   - `~/.roo/skills`, `~/.roo/rules`;
   - globalStorage Zoo.

   Кнопка **Add folder** — для своих папок (заметки, Obsidian, личные папки скиллов).
2. **Сканирование (детерминированно, без модели).**
   - Классификация по месту и форме: `SKILL.md` → скилл; `CLAUDE.md` / `AGENTS.md` / rules → кандидат в ядро; auto-memory → inbox; прочий markdown → кандидат в знания.
   - Разрезание монолитов: журналы с датированными заголовками (`### 2026-08-12 — …`) делятся на записи `experience/`.
   - Хеши файлов: точные копии и расхождения копий одного скилла; для расходящихся копий выбирается новейшая, а конфликты уходят на ревью.
   - Происхождение скилла: `metadata.author` ≠ владелец или git-origin → vendor; неизвестно → adopted.
   - Минимум §4 для каждого скилла и каждого агента.
   - Поиск секретов: найденное в базу не попадает, а показывается.
3. **План (движок §10).** Сжатие кандидатов в ядро до бюджета; слияние почти-дублей (по эмбеддингам); кандидаты в противоречия; раскладка по разделам. На диск не пишется ничего, кроме `.embarsy/migration/plan.json`.
4. **Ревью** — тот же интерфейс, что Inbox: группы, конфликты требуют выбора, ядро — diff в форме Core.
5. **Применение.**
   - Бэкап всех источников в `~/.embarsy/backups/<timestamp>.tar.gz`.
   - Запись базы.
   - Публикация (§6).
   - Запись в `exposure.json`.
   - Кнопка **Undo migration** восстанавливает бэкап и убирает созданные ссылки.
6. **Уборка (отдельно, позже).** Предложение удалить старые копии (например globalStorage Zoo) — каждое место отдельно, с подтверждением.

## 10. Движки и приватность

| Уровень | Чем | Что покрывает |
|---|---|---|
| 1. Детерминированно + эмбеддинги | код Embarsy + встроенная модель эмбеддингов | сканирование, Skills, почти весь Health, почти-дубли, подсказки Inbox по прошлым решениям (поиск ближайших в `decisions.jsonl`) |
| 2. Агент пользователя | Claude / Codex через MCP (`memory_scan`, `memory_propose`) + скилл миграции | план миграции, сжатие ядра, слияния, противоречия |
| 3. Локальная генерация (опция) | Qwen через встроенный Ollama, размер по объёму RAM (≥ 48 ГБ → qwen3.6:35b-a3b; 24–32 ГБ → qwen3.5:9b; 16 ГБ → qwen3.5:4b; меньше — не предлагается) | то же, что уровень 2, без облака |

- Уровень 1 работает всегда. Уровни 2 и 3 пользователь выбирает при онбординге явно; молчаливого значения по умолчанию нет.
- Для уровня 2 UI прямо пишет: содержимое передаётся провайдеру вашего агента. Сам Embarsy в сеть ничего не отправляет.
- Модель уровня 3 не держит ресурсы, пока не нужна. Скачанная — только место на диске. В память её загружает первый запрос Embarsy; каждый запрос уходит с `keep_alive` = время простоя из Settings (1–30 мин, по умолчанию 2), после него Ollama выгружает модель сам. «Unload now» выгружает сразу (`keep_alive: 0`). Состояние «на диске / в памяти, сколько занимает, когда выгрузится» берётся из `/api/ps`, а не из собственного учёта. Скачивание и удаление — из Memory → Assistant, с проверкой свободного места (размер + 5 ГБ); прерванное скачивание продолжается с места остановки.
- Дообучение не входит в v1: нет датасета, задачи разнородные, веса пришлось бы переобучать с каждым релизом модели. Пересмотреть, когда накопится существенный объём решений из inbox.

## 12. Безопасность

- Поиск секретов перед любой записью в базу и при индексации (H12); найденное не индексируется.
- Бэкап до любого изменения мест вне базы; Undo для онбординга и миграции.
- Embarsy меняет вне базы только: ссылки из `exposure.json`, свой блок-маркер в `~/.claude/CLAUDE.md`, `autoMemoryDirectory` и `additionalDirectories` в настройках Claude, MCP-записи (как сейчас в Connections). Каждое изменение видно в предпросмотре.
- Чужие настоящие папки и файлы не перезаписываются никогда.

### Git — история базы для агентов

Git нужен агентам, чтобы видеть, кто, когда и почему изменил память. Пользователю он не показывается.

- Embarsy создаёт локальный репозиторий в папке базы при онбординге, без вопроса и без упоминания в UI.
- Коммитит только операции, применённые кнопкой в UI («Inbox: принято 3 факта от Codex»).
- Правки агентов вне Embarsy (auto-memory, правка через симлинк) перед каждой операцией фиксируются отдельным коммитом «Внешние изменения».
- Атрибуция — трейлерами в сообщении коммита, потому что автор коммита всегда Embarsy:
  ```
  Inbox: принят факт «Go toolchain путь»

  Agent: codex
  Source: inbox/codex/2026-10-11-1402-go-toolchain.md
  Approved-by: user
  ```
  Для внешних изменений агент определяется по месту (`inbox/claude/` → `claude`), иначе `Agent: unknown`.
- Агенты читают историю через MCP `memory_history` (без прав на shell) или напрямую `git -C <база> log / blame`.
- Перед каждым коммитом — проверка секретов (H12): попавшее в историю не удаляется.
- `.git` исключён из индексации `recall`.
- Remote для синхронизации между Mac — скрытая расширенная настройка, по умолчанию выключена.
- Бэкап-архив источников при миграции остаётся: исходные папки вне базы и git их не покрывает.

## Принятые решения

- 2026-10-11 — §10 принят: три уровня движков; облачный уровень включается пользователем явно при онбординге.
- 2026-10-11 — Inbox общий для всех агентов и проектов, включая `autoMemoryDirectory` Claude на уровне пользователя. Это сознательный выбор: пользователь переключается между подписками (Claude, Codex, Zoo) и сохраняет контекст.
- 2026-10-11 — Git в базе ставится всегда и скрыт от пользователя; служит истории и атрибуции изменений для агентов (MCP `memory_history`).
- 2026-10-12 — Если на Mac нет Command Line Tools, истории нет: вызов `/usr/bin/git` без них открывает системное окно установки, поэтому Embarsy ищет git только там, где он реально установлен, и иначе работает без истории.
- 2026-10-12 — База создаётся со стартовым скиллом `embarsy-memory`: как читать базу и как предлагать память через inbox. В фазе 3 его заменят инструменты `recall` / `remember`.
- 2026-10-12 — Фаза 3 разбита на 3a (recall / remember / Inbox) и 3b (миграция). План миграции строит агент пользователя по заданию, которое Embarsy готовит по кнопке.
- 2026-10-12 — Мост находит базу по файлу-указателю `~/Library/Application Support/Embarsy/memory.json`, который пишет приложение, а не по пути в конфиге редактора: перенос базы не требует переподключать агентов.
- 2026-10-12 — База индексируется мостом перед `recall`, если что-то изменилось (не чаще раза в 15 с), в коллекцию `embarsy-memory`, кусками по заголовкам markdown. `inbox/`, `archive/` и `AGENTS.md` (он собран из `core/`) не индексируются. Порог «слабого совпадения» для памяти 0.40 (для кода 0.52): на русской прозе релевантное дало 0.49–0.69, нерелевантное 0.28–0.29.
- 2026-10-12 — Похожие заметки в Inbox ищет приложение через API Embarsy (порог 0.45). Подсказки по прошлым решениям (`decisions.jsonl`) отложены до фазы 4: журнал уже пишется.
- 2026-10-12 — Факты из auto-memory Claude: типы `user` → person, `feedback` → правило ядра, остальное → knowledge; при решении строка удаляется и из `MEMORY.md` Claude.
- 2026-10-12 — Миграция работает во временной папке `~/Library/Application Support/Embarsy/migration/<время>/` (инвентаризация, `TASK.md`, заранее разрезанные записи журналов, план); база создаётся только при применении. Незавершённая миграция переживает перезапуск приложения.
- 2026-10-12 — План ссылается только на файлы внутри выбранных источников и временной папки; это проверяют и мост (`memory_propose`), и приложение (на случай, если агент записал план файлом). Секреты, неверные имена и пути исключают пункт с объяснением.
- 2026-10-12 — При применении старые копии перенесённых скиллов в папках агентов (`~/.agents/skills`, `~/.claude/skills`, `~/.codex/skills`, `~/.roo/skills`) не удаляются, а откладываются в бэкап и заменяются ссылками на базу; повисшие ссылки `~/.roo/skills` тоже откладываются. Копии, которые агент пропустил, откладываются по галочке в ревью (включена по умолчанию). Undo возвращает всё на место. Копии вне папок агентов (личные папки, globalStorage Zoo) не трогаются — их уборка остаётся отдельным шагом.
- 2026-10-13 — Health исправляет сам, кнопками «can fix» и «Fix N issues…», всегда с предпросмотром «было → станет»: битые ссылки (H04) — по карте миграции `.embarsy/migration-map.json` (откуда пришёл каждый файл; для старых баз восстанавливается из применённой миграции), по копиям одного скилла, по единственному совпадению хвоста пути в Spotlight и по корню, найденному для соседних ссылок; ненайденная ссылка снимается с сохранением текста. Номера строк (H05) убираются. Остатки (H20) уходят в бэкап с записью в журнал. Правятся только файлы внутри базы; правки коммитятся с `Source: Memory → Health`. Health теперь проверяет ссылки и в заметках базы.
- 2026-10-14 — Локальная модель переехала из Settings в таб Memory → Assistant («Помощник»): она работает только на память, и там же её просят о помощи. Таб объясняет, что она делает, и управляет моделью; где модель нужна, но не скачана (Health, миграция), кнопка «Set up the assistant» ведёт туда. Модель эмбеддингов осталась в Settings: она общая для поиска по коду и `recall`.
- 2026-10-14 — Меню отражает две опоры Embarsy: Статус · Подключения · Память · Поиск по коду · Настройки. «Поиск по коду» (EN Code search) собирает бывшие «Содержимое», «Активность», «Мониторинг» как свои вкладки «Индекс кода», «Запросы поиска», «Нагрузка»; внутри приложения это по-прежнему три экрана (`AppTab.content/.activity/.monitoring`), так что параметры запуска и сбор метрик не менялись.
